## 4. エンジンの要点(深く入る前に読むところ)

- `engine.js` が計算の全部(画面には触れない)。`ui.js` が画面。先読みは `mc-pool.js` と `mc-worker.js`。
- 推奨手:
  - 先読み無し(貪欲)は `stratB`。中身は `stratB0` で、重みは `PARAMS`(既定)。
  - 商材ごとの上書きは `PRESETS[key].params` に書き、`applyThreshold` が既定の重みに重ねる。
    追加した商材は `ITEM_PARAM_OF` で `ITEM_PARAMS` の組を割り当てる。組は far・farB・farT・farM・tight と、
    元の商材の重みを写した kim(輝紋章の盾)・kham(光の鍛冶ハンマー)・hid(超ようせいのひだね)・orb(虹色のオーブ)・yum(幽紋刀)。
  - アプリは先読み(`stratMCAsync`・`mcPrepare`・`mcRollout`)を使う。先読みの中の試し打ちも、同じ重みで打つ。
  - `stratB0` は、評価の前に決め打ちする手がある(必殺・残り1マスの総当たり・pairSnipe・会心ターンの狙い打ち boostAim・
    boostPlan など)。決め打ちの手は評価関数の重みで止まらないので、集中力を残す判定が別に要る。
- 主な重み:

  | 重み | 意味 |
  |---|---|
  | tcost | 下げた温度を費用に数える |
  | midare・midareW | みだれ打ちを使う |
  | turn・land | 特殊温度に着く手への加点 |
  | heat | 火力上げを始める温度の余裕(判断は「50℃あたり28進む」前提) |
  | cap | 本会心の価値 |
  | adv | 前進の効率の重み |
  | pr | 遅れているマスを優先する度合い |
  | te | 本会心を狙える位置のマスを狙い打つ価値 |
  | rush | ゾーンへ押し込む手の抑制 |
  | mpm | 未到達1マスに残す集中力 |
  | boostAim・boostRes・boostEff | 会心ターンのねらい打ち(撃つ基準・残すマスの数・残り距離) |
  | psEff | 2マス同時の本会心の前に残す集中力(残り距離) |
  | er | 戻りの仕上げのやり直し |
  | lastDP・ldp2 | 最後の1〜2マスの総当たり |

- ゲームの決まりで、間違えやすいもの(利用者の情報):
  - 会心が理想値を通り越す時は、理想値で止まる。すでに理想値以上のマスへの会心は動かない(miss)。
  - 温度は1000℃から始まる。威力は温度で変わる(`scaleUp`)。最初の1手には地金特性が乗らない。
  - 集中の地金: 400の倍数で消費が半分、200の倍数(400の倍数でない)で消費1.5倍・会心が出やすい(どちらも切り上げ。
    meluce.jp の消費の表と一致する)。
  - 戻りの地金: 200の倍数で戻る。戻る量は 12〜16。
  - みだれ打ち: 使うマスからランダムに4回叩く(ゾーン内のマスにも当たる)。
  - 誤差: ゾーン内のマスは差が5以上でも4、ゾーン外のマスは8以下でも9(2017-04-05 の修正。`MAX_ERR`・`OVER_ERR_MIN`)。
- 大成功率の目安(`PRESET_RATES`、先読みあり)は、これまでの9商材にだけある。追加した商材は「検証中」。
  全商材に、先読みなし(貪欲)の参考値 `PRESET_GREEDY` がある(選択欄に「簡易 ◯%」と薄い字で出す。利用者の指示 2026-10-09)。
  9商材の目安は V2.50(決め打ちも先読み)より前のエンジンで測った値なので、測り直すのが望ましい。

## 5. 大成功率の改善

### 5-1. 前のスレッドまで(要約)

### 5-2. メタリオンサイズ(このスレッド)
- 詳しくは `docs/メタリオンサイズの調査.md`。要点:
  - 鎌の許容誤差は公開された値が見つからず、5のまま。5で打っても6で打っても、6で数えた率はほぼ同じ。
  - 打ち方の参考(セーラスサイズ・ステラトルネードの熟練者の手順、集中変化の地金の基本)を集めた。
  - farT は前のスレッドの100局の比較では見落としていたが、2000局では z=6.22 で効いていた。
    **100局の比較は小さい効果を見落とす。** 低い商材は局数を増やして比べ直す価値がある(5-4 の案C)。
  - 効かなかった案: ldp2・会心ターンへの着地の減点・火力上げの基準の変更・余裕の判定の距離化・熟練者の序盤の決め打ち。

### 5-3. 全商材の底上げ(このスレッド)
- 利用者が選んだ進め方: 案A(boostEff)・案B(psEff)を全商材で同じ局どうしで比べ、良ければ既定にする →
  案C(4つの重みの組を、低い商材で局数を増やして比べ直す)。
- **今の率の表(先読み無し・乱数テープ・種44・各1000局):** 戻り以外の133商材を測った(付録の表)。
  - 平均 52.7%、50%未満 61商材。集中力変化55商材は平均 54.4%(50%未満 24)、たたき変化・威力会心率上昇78商材は
    平均 51.5%(50%未満 37)。
  - 戻りの36商材も、検証を速くした後に測った: 平均 51.4%(50%未満 18)。全169商材では平均 52.4%、50%未満 79、到達90%未満 21。
- **案A(boostEff を集中力変化の全商材の既定にする):** 種44・各1000局・同じ局どうし。
  4: 大成功かどうかが変わった局があったのは16商材、全体で片方だけ大成功 390局対430局(z=1.40)。5: 8商材、68局対84局(z=1.30)。
  悪くなる商材(z≤-2)は無いが、上がり幅が小さいので既定にはしていない。到達率は遠い商材で上がる
  (セーラスサイズ 72.8 → 76.3%、呪星のツメ 83.2 → 87.0%)。
- **案B(psEff 4):** 終わった23商材・2万3千局で、大成功かどうかが変わった局が1つも無かった。効果が無い見込みで、比較を打ち切った。
- **失敗の内訳(50%未満の61商材、種44):** 届かない 6.7% / 超過 5.3% / **届くが誤差超え 46.2%**。

  誤差超えの局(2万8千局)の、各マスの最後の一打:

  | 最後の一打 | 1局あたり | 誤差0の割合 |
  |---|---|---|
  | 狙い打ち系・通常の温度・本会心を狙える位置 | 1.52回 | 42% |
  | 狙い打ち系・通常の温度・位置の外 | 0.72回 | 53% |
  | ふつうの技・通常の温度・本会心を狙える位置 | 0.71回 | 17% |
  | 狙い打ち系・会心ターン・狙える位置 | 0.30回 | 65% |

  狙える位置でふつうの技を打つ手(誤差0は17%)と、通常の温度の狙い打ち(会心ターンなら65%)に伸びしろがある。
- **難航商材:** 到達率も大成功率も低かったレイヴンサイズ(鎌・光)とウィズダムサイス(同じ形・同じ地金)は、
  光の地金の重みの組で 37→59% 前後に上がった。重みの細かい探索も始めたが(cap 18・pr 0.3 で数pt)、利用者の指示で止めた。
  光の組の上に、温度の費用(tcost)・残り距離で慎重にする(safeK)・火力上げの基準(hstep)を足すと、到達は上がるが大成功は下がった。
- **重みの組の見直し(案C を広げたもの):** 10の組を追加160商材に当て、種44でふるい分け → 種55で確かめて64商材に入れた。
  上がり幅 +3.6〜+21.4pt、169商材の平均で +4.1pt(先読み無し)。詳しくは `docs/重みの組の見直し.md`。

| 案 | 内容 | 良い点 | 悪い点 |
|---|---|---|---|
| 組の見直しの続き | 見直しで入らなかった商材(z<3)に、組の組み合わせ(例: 光の組+火力上げ)を当てる | エンジンを変えないので他の商材に影響しない | 1組ずつの差は小さくなり、局数が要る |

## 6. 確かめ方(手順とスクリプト)

- 成績テスト: `node tests/sim.js`(これまでの9商材。基準と照合。このスレッドでは4コアで12分)。
  - 推奨手を変えたら、確かめたうえで `--update` を実行する。追加した商材は成績テストに入っていない。
- 1商材の分析:
  `node tools/analyze.js --preset 名前 --games 1000 --tape 1 --seed 22 --params '{"tcost":0.017}' --log 記録.jsonl`
  - `--tape 1` にすると、同じ局どうしで比べやすい。`--preset` には追加した商材の名前も使える。
  - **注意:** `--log` に同じファイルを渡すと、記録済みの局は打たずに飛ばす(続きから再開する機能)。
    設定を変えて比べる時は、必ず新しいファイル名にする。
- 同じ局どうしの比べ方: 片方だけ大成功した局の数を a 対 b とすると、z = (b − a) / √(a + b)。

```js
// node pair.js 記録A.jsonl 記録B.jsonl
const fs = require('fs');
const rd = f => Object.fromEntries(fs.readFileSync(f, 'utf8').trim().split('\n').map(JSON.parse).map(r => [r.g, r]));
const [x, y] = process.argv.slice(2).map(rd);
let n = 0, A = 0, B = 0, a = 0, b = 0;
for(const g in x){ if(!(g in y)) continue; n++; A += x[g].great; B += y[g].great;
  if(x[g].great && !y[g].great) a++; if(y[g].great && !x[g].great) b++; }
console.log(`n ${n} 大成功 ${A} → ${B} 片方だけ ${a} 対 ${b} z=${((b - a) / Math.sqrt(Math.max(1, a + b))).toFixed(2)}`);
```

- 全商材を打つ(このスレッドで使ったもの。scratchpad の場所 `$S` は書き換える)。
  商材の一覧は `PRESET_ORDER` を1行に1つずつ書いたファイル(地金ごとに分けると、遅い戻りを後回しにできる)。

```bash
#!/bin/bash
# sweep.sh 名前 種 局数 'params(JSON)'   一覧のファイルは環境変数 KEYS で渡す
S=/path/to/scratchpad
name=$1; seed=$2; games=$3; params=${4:-'{}'}
out=$S/sweep/$name; mkdir -p "$out"
cd /home/user/KajiTool_V3
export seed games params out
cat ${KEYS:-$S/sweep/keys.txt} | xargs -P 4 -I{} sh -c 'node tools/analyze.js --preset "{}" --games $games --tape 1 --seed $seed --params "$params" --log "$out/{}.jsonl" > /dev/null 2>&1 || echo "失敗 {}"'
echo "終了 $name"
```

```bash
# 商材の一覧を地金ごとに作る
node -e "const fs=require('fs'),vm=require('vm');vm.runInThisContext(fs.readFileSync('engine.js','utf8'));
const P=vm.runInThisContext('PRESETS'),O=vm.runInThisContext('PRESET_ORDER');
for(const t of ['shuchu','tataki','kaishin','modori']) fs.writeFileSync('keys_'+t+'.txt',O.filter(k=>P[k].trait===t).join('\n')+'\n');"
```

  - 2つの名前の記録を、商材ごとに pair.js と同じやり方で突き合わせ、全体の a 対 b と、商材ごとの z を出す。
  - `--params` は商材の重みの上に重なる(商材がもともと持つ重みは残る)。
- 組み込んだ後の確認: 重みをエンジンに入れたら、`--params` 無しで同じ種を打ち直し、確かめた時の記録と全局一致することを確かめる。
- 変更の後は `python3 tools/stamp.py`(ファイルの版の印)を実行してからコミットする。

## 7. はまったところ(繰り返さないために)

- **裏で動かした処理が止まる。**
  - Bash の `run_in_background` は最大2時間で止められる。長い比較は段階に分け、止まったら同じコマンドで再開する
    (`--log` の記録から続く)。止めた処理の最後の行が途中で切れていることがあるので、再開の前に確かめる。
  - nohup で動かした比較が、知らない間に止まっていたこともある。
- `pkill`・`pgrep -f` の使い方によっては、自分のシェルを止めてしまう(終了コード144)。PID を指定して止める。
  `pgrep -x node` で node だけを拾い、`/proc/PID/cmdline` で中身を確かめてから止めると安全。
- 自作のスクリプトでエンジンを `vm.createContext` の隔離環境に読み込むと、約10倍遅い。`vm.runInThisContext` で読み込む
  (`tests/sim.js` と同じ)。1プロセスに1つのエンジンしか読めないので、2つのエンジンを比べる時はプロセスを分ける。
- 走っている測定が engine.js を読み直す作り(率の測定は商材ごとに `tools/analyze.js` を起こす)だと、途中で engine.js を変えると
  前後で別のエンジンの局が混ざる。変える前に記録の数と走っている仕事を控え、前のエンジンの局は別のファイルに移す。
- シェルの変数を使った `rm` は止められることがある。`"${S:?}"` の形にするか、新しいディレクトリを使う。
- 先読みありの分析は1局に数十秒〜数分かかる。何百局も回すと何時間もかかる。
- **戻りの地金の商材は、先読み無しでも遅かった**(奇跡の鍛冶ハンマーは35分で429局)。原因は総当たりの表の上限(24MB)で、
  表の作り直しを繰り返していた。検証のスクリプトでは上限を 4GB にして解決した(アプリは 24MB のまま)。
- **`tools/tune.js` は乱数テープを使わない。** 1局の手順が変わると以降の局の乱数が全部ずれるので、比べるたびのばらつきが大きい
  (差の標準誤差 約1.3pt)。記録される「一番良かった値」も高めに出る。探索の後は、別の種・乱数テープ・同じ局どうしで確かめる。
- 自作の探索で、仕事のたびにエンジンを読み込み直すと、最後の1マスの総当たりの表を毎回作り直して何倍も遅くなる。
  エンジンは使い回す(重みを変えても `applyThreshold` が毎局戻すので、結果は同じになることを確かめた)。
- 多くの案から選ぶと、偶然 z≥2 になるものが混ざる。必ず、選ぶのに使っていない種で確かめてから入れる。
- 1商材100局の比較は、小さい効果を見落とす(farT のメタリオンサイズ)。
- DQ10大辞典(wikiwiki.jp)は、この作業の環境からは閲覧を拒否される。冒険者の広場の日誌は curl で読める
  (WebFetch はログイン画面に飛ばされる)。
